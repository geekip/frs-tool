# Release policy

FRS-TOOL v1 releases are built with Go 1.24.13, `CGO_ENABLED=0`, `-trimpath`, no VCS stamping, and a cleared linker build ID. A release tag must match `vMAJOR.MINOR.PATCH`; the same tag is embedded in `frs version`.

The release workflow tests and runs all eight targets before publishing:

| Operating system | Architectures | Archive |
|---|---|---|
| Linux | amd64, arm64 | `.tar.gz` |
| macOS | amd64, arm64 | `.tar.gz` |
| Windows | amd64, arm64 | `.zip` |
| FreeBSD | amd64, arm64 | `.tar.gz` |

Each archive contains the executable, `README.md`, and `config.example.json`. Archive paths, order, modes, owners, timestamps, compression settings, and build flags are fixed. `SHA256SUMS` covers all eight archives. The workflow compares the complete FRS bytes generated by every platform before it creates a draft release, and only publishes that draft after all assets are present.

## Minimum systems

- Linux 5.10 or newer. This is the product support floor even though the locked Go toolchain can run on older kernels.
- macOS 11 Big Sur or newer.
- Windows 10 or Windows Server 2016 or newer.
- FreeBSD 12.0 or newer for amd64 and arm64; the release workflow validates both architectures on FreeBSD 14.3.

The macOS floor follows the [Go 1.24 release notes](https://go.dev/doc/go1.24), while the Windows and FreeBSD floors follow Go's [minimum requirements](https://go.dev/wiki/MinimumRequirements) and [FreeBSD support matrix](https://go.dev/wiki/FreeBSD). These promises cover local filesystems with reliable process locks and same-directory atomic replacement. NFS, SMB, FUSE, and other network or special filesystems are outside the v1 guarantee.

HTTPS downloads use the target system certificate store. Release archives do not bundle CA certificates, DNS configuration, network settings, or rule data.

## Release workflow

Pushing a version tag runs `.github/workflows/release.yml`. The workflow:

1. validates the tag, exact Go toolchain, tests, vet, and race checks;
2. runs the full suite and archive smoke tests on native Linux, macOS, and Windows runners and real FreeBSD virtual machines for both architectures;
3. exercises the archived executable with `version`, `verify`, `inspect`, a fixed-input build, process locking, and injected publish failures;
4. requires byte-identical FRS output from all eight targets;
5. benchmarks the frozen 10/3/5 defaults on three real self-hosted Linux machines labeled `frs-low`, `frs-medium`, and `frs-high`, records their CPU, memory, throughput, and peak RSS evidence, and verifies that their hardware grades are strictly increasing;
6. generates and checks `SHA256SUMS`, creates a draft release, and publishes it only after every asset is uploaded.

The three benchmark runners also carry the standard `self-hosted`, `linux`, and `x64` labels. A repository without all three real hardware tiers cannot publish a formal v1 release; cross-compilation or resource throttling on one host is intentionally not accepted as a substitute.

No package-manager bundle, installer, container image, or automatic updater is part of v1.
